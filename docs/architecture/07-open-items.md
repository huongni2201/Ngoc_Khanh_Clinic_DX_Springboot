# Open implementation and decision items

Reviewed against the worktree on 2026-10-09. This page replaces the unfinished
endpoint-authorization and document-template implementation plans. It records
remaining work, not accepted permissions, schema changes or deployed features.

## Endpoint authorization

`EndpointPermissions` reads the 25 business endpoint mappings stored by V002 at
startup under [ADR-0015](../adr/0015-endpoint-permission-rbac.md). The former route
gaps are closed: Organization DELETE uses `ORGANIZATION_DELETE`, Batch DELETE uses
`HEALTH_EXAMINATION_BATCH_DELETE`, and catalog service lookup uses
`SERVICE_CATALOG_VIEW`. All are granted to CLINIC_MANAGER. Local TEST and
ADMINISTRATOR accounts receive all permissions from the local seed and use the
same HTTP checks; no role bypasses unmapped endpoints.

Organization/Batch writes currently accept an actor UUID; their reads and catalog
reads do not receive a principal. HTTP rules protect mapped requests, but direct
application callers lack equivalent permission checks. Participant and examination
detail policies already check their principals. The owning business modules must
protect non-HTTP callers under the accepted action/scope contracts as well.

V002 still contains legacy Participant permission codes and grant clauses for
`ADMIN`; the role matrix uses `ADMINISTRATOR`, and runtime Participant routes use
`PARTICIPANT_*`. Do not treat the legacy grants as runtime permission mappings or
infer production grants from the local-only all-permission grants.

Completion requires an accepted method/path/account-type/permission/grant matrix,
matching HTTP and application enforcement, and coverage of all business mappings.
Verify wrong account type, missing permission, literal-before-wildcard ordering,
direct application callers and seed-to-session authorization. Permission snapshots
refresh on sign-in; automatic revocation on grant change is still missing.

## Session go-live blockers

The session mechanism and per-endpoint rules exist. Login rate limiting,
logout-all/automatic revocation and production Origin/CSRF review remain open in
[ADR-0014](../adr/0014-session-cookie-redis-login.md#go-live-blockers).
Equivalent authorization for direct Organization/Batch/catalog application callers
also remains unfinished; the former HTTP route gaps are closed.

## Official document issuance

The document module contains schema records, an effective master-template query and, since
the [examination-form print](../api/examination-form-print.md) slice, an on-demand DOCX→PDF
renderer (JDK DOM engine + Gotenberg) with a seeded starter template. No current HTTP
workflow issues official documents or stores a rendered PDF snapshot. Still open for that
slice: barcode verification on the clinic's printer and scanner, a "my print jobs" list (the front end keeps only
the last job of the tab; [print jobs](../api/examination-form-print-jobs.md)), parallel rendering, object storage for parts,
and a production deployment of Gotenberg without Internet egress. Decision record:
[ADR-0017](../adr/0017-document-rendering-and-template-lifecycle.md) (proposed). The Excel roster, reconciliation workbook and payment-report DOCX
are already generated by health examination under their
[API contracts](../api/examination-details-and-report.md); they do not establish
an official-document issuance pipeline.

Template editing/upload/publish APIs and screens are excluded by accepted
[ADR-0018](../adr/0018-it-managed-document-templates.md), not deferred implementation
work. Business/clinical staff approve content; IT validates and releases a new
immutable version through a reviewed release/migration. Existing rendering,
template-version storage and historical protections remain required.

The removed plan proposed templates versioned in the repository, typed models
owned by business modules, immutable PDF snapshots at issuance and byte-identical
reprints. It also proposed a DOCX engine, a separate PDF conversion service and
object storage. These choices need an accepted rendering/storage ADR before
implementation. No engine, sidecar or production storage provider is selected.

Decisions still required:

- Whether to persist PDF snapshots and extend `issued_representations` with a
  rendered-file reference; the current schema has no `rendered_file_id` or template
  `contract_version` column.
- Which first business issuance workflow supplies the official source version,
  permissions, idempotency and transaction contract.
- Template lifecycle: the current protection trigger prevents retiring a template
  version already referenced by an issued representation. Any change must preserve
  issued content and references.
- Rendering engine compatibility, conversion service, Vietnamese fonts, storage,
  checksums and authorized download behavior.
- How to recheck the source version after rendering, record issuance and audit
  atomically, and clean orphaned objects when persistence fails.

Acceptance requires an approved business/storage contract, a reviewed migration
when needed, immutable issued-version/reprint checks, rollback/concurrency/
idempotency tests and visual verification of Vietnamese output. User-uploaded
templates and a template-management UI are excluded by ADR-0018.

## Applying future changes

Use a new migration after the highest current version for future schema or grant
changes. The V001–V003 consolidation is a fresh-database baseline, not an upgrade
procedure for existing data. Verify affected PostgreSQL/Redis checks and the Maven
wrapper under [operations](06-testing-and-operations.md); report unavailable
dependencies and skips. This page makes no runtime test-success claim.
